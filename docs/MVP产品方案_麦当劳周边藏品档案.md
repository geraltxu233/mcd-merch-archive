# MVP 产品方案：麦当劳周边藏品档案

> 版本：v0.1（讨论稿）｜ 日期：2026-10-10 ｜ 形态：WorkBuddy skill 包 + GitHub 参赛仓库
> 本文标注【事实】= 已由 MCP 实测确认；【假设】= 需验证；【待定】= 尚待确认

> **落地情况（2026-10-10 补记）**：本文为设计阶段方案。实际落地时，第四节第 5 项「个人联动」**未实现** —— 原因是积分商城在售周边类目为空，联动无数据可展示；`README.md` / `MCP_INTEGRATION.md` / `SKILL.md` 中的相关表述已同步修正为「获取路径指引」。其余各项均已落地。

## 一、一句话定位

**给关注麦当劳周边、又不想被小红书碎片信息牵着走的玩家，一本能一直查、能对比、能追溯的麦当劳中国周边藏品档案。**

解决的不是"值多少钱"（数据上做不到，见第五节），而是"**这东西是什么、怎么拿到的、现在还能不能拿、有多稀缺**"。

---

## 二、用户与场景

### 目标用户（分层，不写"所有年轻人"）

| 层 | 是谁 | 处境 | 核心诉求 |
|----|------|------|---------|
| 主力 | 收藏向成年玩家 | 抢过对讲机/联名款，家里有一堆周边 | 不遗漏、不重复、知道还差哪件 |
| 次主力 | 想入坑的新人 | 看到别人晒但信息零散 | 快速搞懂"这是什么、还能拿吗" |
| 资产层 | 有积分的会员 | 积分快过期，不知道能换什么 | 积分能换哪些周边 |
| 传播层 | 围观者 | 不买，但爱看 | 一眼看到"最稀有的那件"，可截图 |

### 场景还原（主力用户）

```
触发：刷到有人晒 GD 联名徽章 → 想确认"我错过了吗 / 后面还有几弹"
现状：翻小红书碎片帖、问群友、翻 App 活动页 → 信息散、看过就忘、查不到历史
结果：要么错过，要么花大量时间搜集
阻力：没有一处结构化的、可追溯的周边档案
```

## 三、需求真实性判断

| 判别三问 | 回答 | 判断 |
|---------|------|------|
| 现在你怎么解决？ | 小红书碎片 + 群聊 + App 活动页，无结构化档案 | 替代方案很差 |
| 多久发生一次？ | 约每月一档周边上新（10 月为每周一档），收藏玩家持续关注 | 【事实】频次中高 |
| 愿意付出什么代价？ | 愿意花时间蹲点抢（对讲机加购当天 App 瘫痪即为证据） | 意愿真实，但"用不用档案"未验证 |

**结论**：需求真实性【估计中高，付费/使用意愿待验证】。真正的验证动作是——把档案发出去，看有没有人转发、有没有人喊"再来一版"。**这就是 MVP 要验的第一个假设。**

## 四、MVP 边界

### 做（构成完整闭环：采集 → 归档 → 查阅）

| # | 模块 | 内容 | 为什么在 MVP 里 |
|---|------|------|----------------|
| 1 | **藏品库**（单一数据源） | JSON/Markdown 一张表，一条=一件藏品 | 没有库就没有一切 |
| 2 | **采集器** | 调 campaign-calendar + mall-points-products，自动抽取为藏品条目 | 这是"MCP 驱动"的证据，也是生长引擎 |
| 3 | **档案视图** | 按时间线的图鉴卡片（每件一张卡） | 用户直接消费的形态 |
| 4 | **榜单视图** | 按稀缺度指数排序 | 可截图传播的门面 |
| 5 | **个人联动** | 调 query-my-account，显示"你的积分能换哪些" | 制造"这跟我有关" |

### 不做（MVP 砍掉，写清理由）

| 砍掉 | 理由 |
|------|------|
| 二级市场价 | 无数据源，属 B 阶段（你选的 C 里的后半段） |
| 门店库存查询 | 【事实】MCP 门店接口无库存字段，技术上不成立 |
| 自动订阅/推送 | 成本高、依赖长期运行，MVP 不验这个 |
| 下单/兑换/抽奖 | 红色区工具，作品演示禁碰 |
| 全量开心乐园餐玩具 | 【事实】MCP 无该数据源；只能人工补录少量经典款作为"历史条目" |

## 五、数据架构

### 数据来源与主次（已修正）

| 源 | MCP 工具 | 提供什么 | 角色 |
|----|---------|---------|------|
| 活动日历 | campaign-calendar | 周边发售活动、加价购金额、限量文案、发售时间 | **主源** |
| 积分商城 | mall-points-products | 积分价、上架/下架时间、限量份数 | 辅源 |
| 个人资产 | query-my-account | 可用积分 | 联动 |
| 人工补录 | 无（手工） | 历史爆款（对讲机、俄罗斯方块机等） | 冷启动 |

### 三条硬约束（均为【事实】实测确认）

1. **历史不可回溯**：活动日历只保留近期窗口，传历史日期无效 → 历史只能自己攒。
2. **status 不可信**：商城里大量 status=2（上架）但 downTime 已过期 → 一律按时间窗自行过滤。
3. **积分商城玩具极少**：全量 46 条里玩具/实物仅 2 条且已过期 → 不能指望它出料。

### 单一数据源原则

```
藏品库（唯一数据源）
   ├─→ 生成 图鉴视图
   ├─→ 生成 榜单视图
   └─→ 生成 个人联动视图
```
任何信息只在藏品库维护一次，视图全部从中派生，禁止各视图各存一份。

## 六、稀缺度指数（SI）定义

> **诚实声明**：SI 衡量的是"稀缺信号强度"，**不是市场价格、不是升值潜力**。禁止用 SI 暗示"值多少钱"。

| 维度 | 数据来源 | 打分逻辑 | 权重【假设，待校准】 |
|------|---------|---------|------------------|
| 限量程度 | 文案文本 | 明确"限量 N 份"按 N 越小分越高；无明确限量给中位分 | 30% |
| 获取门槛 | 加价购金额 / 积分价 | 门槛越高分越高；免费加购分低 | 20% |
| 发售窗口 | upTime/downTime | 窗口越短分越高（2 小时 > 1 个月） | 20% |
| 售罄状态 | status + 自采样 | 已售罄/已结束 = 稀缺既成事实，分高 | 20% |
| 联名 IP | 文案 | 知名品牌联名分高，自有 IP 中，无联名低 | 10% |

每维度 0~5 分 → 加权求和 ×20 → **SI 0~100**。算法公开、数据可溯源、可复现（同一输入两次计算结果一致）。

**权重是【假设】**，需要后续用"哪些藏品在社媒被讨论最多"来反向校准——这是二期的事。

## 七、用户故事

1. 作为收藏玩家，我要在一处看全所有周边藏品，以便不遗漏、不重复收集。
2. 作为新人，我要知道每件藏品怎么获得、还能不能拿，以便决定要不要入手。
3. 作为有积分的会员，我要知道积分能换哪些周边，以便决定攒还是花。
4. 作为围观者，我要一眼看到最稀缺的几件，以便截图分享。

## 八、验收标准（可测量、可判定）

| # | 标准 | 判定方式 |
|---|------|---------|
| 1 | 藏品库 ≥ 20 条 | 数条数（当前窗口 3 条 + 冷启动 ≥ 17 条） |
| 2 | 每张卡 ≥ 6 个字段完整 | 字段非空率检查 |
| 3 | 采集器 1 次调用完成当前活动抓取并结构化 | 跑一次看输出 |
| 4 | SI 可复现 | 同数据两次计算完全一致 |
| 5 | 全流程仅调用绿色区工具 | 检查调用日志 |
| 6 | 每个字段可溯源（MCP 返回 or 标注"人工补录"） | 抽查 |
| 7 | 无编造数据 | 抽查（应为 0 编造） |

## 九、冷启动策略（关键）

因为历史不可回溯，**必须人工补录才能让档案立刻有料**。冷启动素材来源：

1. 你已整理的两份情报文档（"大人抢玩具出圈案例"表 = 现成素材）
2. 公开可考的历史爆款：麦麦对讲机、麦乐鸡俄罗斯方块机、Teenie Beanie 豆豆娃、40 周年复刻系列等
3. 每条标注来源为"人工补录"，与 MCP 自动采集条目区分开，保证数据诚实

**【假设】** 冷启动 15~20 条足以让"图鉴 + 榜单"看起来有内容。需实测。

## 十、路线图（15 天，每个里程碑=一次假设验证）

| 里程碑 | 时间 | 交付 | 验证的假设 |
|--------|------|------|-----------|
| M1 数据层 | 10-11~10-13 | 藏品库 + 采集器跑通 | "MCP 数据能被结构化归档" |
| M2 视图层 | 10-14~10-17 | 图鉴视图 + 榜单视图 | "档案形态有人看得懂" |
| M3 门面层 | 10-18~10-21 | 可截图卡片 + skill 封装 + 六件套文档 | "门面能脱离 skill 独立传播" |
| M4 发布层 | 10-22~10-25 | GitHub 发布 + 报名 Issue + workbuddy.md + 传播物料 | "有人愿意点 Star" |

**风险**：M1 若卡在"文案里抽不出限量信息"（NLP 解析不稳定），则退化为人工录入为主、自动采集为辅。

## 十一、风险与依赖

| 风险 | 影响 | 应对 |
|------|------|------|
| 15 天数据太薄 | 榜单不够看 | 冷启动补录 |
| 采集器需长期运行 | 比赛期只能证明机制 | 用"机制完整度"替代"数据量" |
| 文案解析不稳定 | 自动化率低 | 降级为半自动（脚本抽取 + 人工确认） |
| 社群无反应 | Star 起不来 | 门面必须可截图、必须有情绪钩子 |
| 合规风险 | 取消资格 | 只捧不贬、不做品牌对比 |

**依赖**：MCP token 有效性、GitHub 账号、小红书/传播渠道（可选）。

---

## 十二、合规红线（锁死）

1. 只做资讯/档案视角，**不得贬损麦当劳、不得与其他品牌做对比**。
2. 演示只用绿色区工具；红色区工具仅在 MCP_INTEGRATION.md 做"能力声明"，不实际调用。
3. 个人数据（积分/卡包）截图必须脱敏 accountId。
4. 人工补录条目必须标注来源，与 MCP 数据区分。
